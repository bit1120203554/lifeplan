# Agent 评测与工程：怎样知道它是否真的做好了

Agent 一次任务可能经历多次模型调用和工具执行，所以只看最后一句回答是否流畅不够。本篇从可复现的任务、评分和比较开始，再讲日志、可靠性和面试中可展示的小实验。

## 1. 先定义任务、环境和成功

一个评测任务至少要写清：输入是什么、Agent 可用哪些工具、环境初始状态、资源预算、成功标准，以及如何恢复初始状态。例如：

> 在一个只读笔记库里，回答“实验 A 与 B 的预算各是多少”，同时引用各自笔记。限制最多 4 次检索、30 秒。两个数字都正确且引用确实支持，才算任务成功。

一条 task 是一个题目；trial 是某系统在该任务上的一次运行；多次 trial 可以观察随机性。**测试环境**应尽量与真实任务相近，但也要隔离外部写入并控制版本。数据集被反复用于调提示就变成了开发集，不能再作为独立最终测试。

Agent 的可观察对象包括：最终结果、外部环境的最终状态、每一步工具与参数、真实观察、模型输出、耗时及 token。成功应依据任务目标判断；达到格式不代表真的完成，工具调用成功也不代表答案正确。

## 2. 三类评分器，组合使用

| 评分器 | 机制与优点 | 典型缺陷 |
|---|---|---|
| 规则/代码 verifier | 数值核对、单元测试、文件差异等；快且易复现 | 检查项可能不全，字符串严格匹配会误杀正确变体 |
| LLM-as-a-Judge | 根据 rubric 判断开放答案质量或两两比较 | 有位置、长度、模型偏好等偏差，评分可能不稳定 |
| 人工/专家 | 对复杂事实和含义做判断 | 贵、慢，不同标注者也会有分歧 |

**Rubric**是明确的评分标准，例如“数字是否正确、引用是否能支持数字、未找到资料时是否承认”。给 judge 输入题目、答案、必要证据与标准，要求结构化结果与依据；不要让它仅凭流畅程度打分。拿人工标注样本校准 judge，关注与人一致率及错误类型、不同位置顺序结果；盲测、互换 A/B 顺序、抽样复核。隐藏参考答案、数据污染和评审模型与被测模型同源也要考虑。

代码测试也只是其覆盖条件的判据：一份代码通过弱测试，不代表所有功能都正确；缺少重要测试会让系统“刷分”。

## 3. 指标：效果、可靠性和成本一起看

**任务成功率**=成功 trial 数/总 trial 数；对每任务多次运行时，先说明是按运行还是按任务平均。示例：10 道题各跑 2 次，14 次成功，则运行级成功率 70%；但不能据此断定 14 道题成功，因为总共只有 10 道题。

**工具调用成功率**=被成功执行的调用数/发起调用数；它不是任务成功率，调用成功却查错文件仍会失败。还需看参数合法率、超时、恢复率、引用支持率、完成时间、输入/输出 token、费用、安全违规等。p50 是第 50 百分位延迟，p95 是第 95 百分位；平均值会掩盖慢尾。

**pass@k**表示在同一任务采样 k 个候选时至少一个正确的概率；它评估候选覆盖，不等于系统最终选出的答案准确率。若实际独立采样 k 次后直接检查，任务级可记录是否至少有一个通过。对于 n 个候选中 c 个正确，常用无放回组合估计量：
\[
\widehat{\mathrm{pass@k}}=1-\frac{\binom{n-c}{k}}{\binom nk},\quad n\ge k.
\]
例如 n=4、c=1、k=2，结果为 1−C(3,2)/C(4,2)=0.5。估计所需采样方式、独立性与任务分布应说明；若系统额外运行选择器，选择器输出的成功率要另报。

**成本与延迟**：把模型调用、搜索/检索、验证器、工具和人工介入一并计入；有条件报告成功任务的平均成本与失败任务成本。多次候选或反思若比基线成功率高，但费用翻倍，要在相同预算或成本—效果曲线下比较。

## 4. 设计公平、可复现的对照

例如你想验证“把失败案例摘要加入下一轮上下文是否提高成功率”：

1. 固定任务集、模型及版本、工具、环境、成功判据和最大预算。A 是现有方式，B 仅增加失败摘要；先说清其生成是否额外花调用。
2. 每道任务均运行 A/B，记录相同问题和各自完整轨迹，尽可能控制随机种子；模型服务不保证种子可完全复现。
3. 报任务级配对差异：多少题 A/B 同成功、A 成 B 败、A 败 B 成、同失败；多次运行报告不确定性，不仅看某次平均。
4. 检查失败切片：检索失败、工具参数错、验证器漏判、摘要引入错误等；抽样人工看证据。
5. 保留未接触的测试任务，开发结束后冻结设置，最终在独立环境运行；记版本、全部成本、随机性和限制。

如 B 有额外预算，应同时报告等预算结果或明确不等预算。任务若按关卡/仓库具有家族相似性，随机打散可能泄漏，最好按环境/来源分组划分。模型预训练数据污染、题目已公开也可能影响结论。小样本不支持精确推断总体收益。

## 5. 实验日志与排查：从失败回溯到哪一步

一条 trace 可包含 run_id、task_id、模型/提示/工具/数据版本、每个调用的开始结束时间、参数及返回、错误类型、token 和费用、最终状态与评分。注意脱敏、权限与保留期限。真实系统的 span 可以表示一次模型调用或工具调用，父子关系拼成一次请求；trace ID 方便串联。

一个可执行的排错顺序：

1. **任务失败是真失败吗？** 检查评分器、初始环境和任务定义。
2. **有没有足够信息？** 看文档是否存在、检索是否召回、证据是否进入上下文。
3. **决策对吗？** 看选择工具、调用顺序、参数与预算是否合理。
4. **执行是否真实成功？** 读工具返回、异常、超时与外部状态，不只看模型总结。
5. **最终结果受支持吗？** 检查引用、计算和任务约束；划分最早可确认的失败点，但多种因素可共同导致失败。

### 可运行的轻量指标示例

```python
def summarize(rows):
    # 每行一次 trial；success 必须为布尔值，tokens 为非负整数
    if not rows:
        return {"trials": 0, "success_rate": None, "avg_tokens": None}
    for row in rows:
        if not isinstance(row["success"], bool) or row["tokens"] < 0:
            raise ValueError("记录不合法")
    return {"trials": len(rows),
            "success_rate": sum(r["success"] for r in rows) / len(rows),
            "avg_tokens": sum(r["tokens"] for r in rows) / len(rows)}

print(summarize([{"success": True, "tokens": 100},
                 {"success": False, "tokens": 200}]))
# {'trials': 2, 'success_rate': 0.5, 'avg_tokens': 150.0}
```

这是最小统计，不包含置信区间、重复任务权重、分组或真实 token 计费。生产日志还需要校验数据类型、脱敏及异常处理。

## 6. 工程化问题：并发、超时、可靠性

- **同步/异步**：等待外部模型或检索服务时可用异步提高并发；CPU 密集任务不一定因 async 自动并行。限制并发量与队列，防止触发限流或雪崩。
- **超时/重试**：区分模型调用超时和工具执行超时；有限重试、指数退避可应对暂时性故障，但非幂等写操作需先确认是否已经执行。
- **缓存**：缓存相同查询、embedding 或可复用工具结果可降成本；应记录模型/数据/权限版本和过期条件，避免泄露或使用旧事实。
- **降级**：搜索或模型不可用时，可返回明确失败、只读结果或请求人工介入；不应以编造补齐。
- **可恢复**：保存任务状态和已完成操作 ID；恢复前核验外部状态。并发写入需要一致性/冲突控制。
- **安全**：外部网页、检索片段和工具返回都是不可信输入，执行工具须独立校验权限；模型生成的代码须隔离。更多见[Agent 安全](agent-harness.md)。

## 7. 将你的研究变成低负担练习

目标是**检验一个真实问题**，不必另造大项目。若现有研究允许，可选取少量已能公开使用的日志/合成任务，做一个“候选策略检查与失败归因”的本地小实验：

1. 定义 10—20 个可重复运行的开发任务，保留任务 ID、输入、正确判据与环境版本。若没有合适真实任务，先用公开或自造玩具任务，并写明来源。
2. 实现最简单基线：固定工具调用顺序、固定候选或不使用反馈。明确定义失败判据和预算。
3. 接入你已有的可执行校验或模拟器；把任务、候选、观察、结果存成 JSONL。不要自动执行未审查的任意模型代码。
4. 做一个具体变化，例如错误类别摘要；固定其余条件，比较成功、失败类型与调用成本。预留未看过的测试任务。
5. 整理一页报告：问题、实现、样例轨迹、结果、局限及下步。没完成就标记计划，没显著提升就如实记录。

时间可分三次各 60—90 分钟：第一次定义任务和基线，第二次跑校验与记录，第三次做对照和复盘。科研与求职资料能共用，但不能臆造结果或未经确认公开研究代码/数据。

## 8. 常见基准与框架怎么理解

**SWE-bench**以软件仓库任务与测试衡量代码修复；Verified 是人工筛查的子集。运行环境、工具、模型、预算都会影响结果，不同设置的榜单不能只看数字。测试覆盖、泄漏和分布差异也会影响外推。

**BFCL**关注模型函数调用能力，涵盖不同工具调用场景；测试格式和版本变化，应注明具体版本与设置。通过工具调用基准不等于能可靠完成长任务。

按场景再认识几个基准，记住“测什么和怎么判定”比背分数有用：

| 基准 | 任务及判据重点 | 不能由此直接推出 |
|---|---|---|
| [ToolBench / ToolLLM](https://arxiv.org/abs/2307.16789) | 多种真实 API 的工具选择与调用，含构造数据和自动评价 | API 可用性、评审方式与当前业务一致 |
| [WebArena](https://arxiv.org/abs/2307.13854) | 在可复现网页环境执行多步任务，检查任务功能结果 | 在任意真实网站权限、数据和规则变化下同样可靠 |
| [τ-bench](https://arxiv.org/abs/2406.12045) | 模拟用户对话、领域工具及业务规则，比较最终数据库状态 | 模拟用户覆盖所有真实用户行为 |
| [OSWorld](https://arxiv.org/abs/2404.07972) | 在操作系统和应用中完成跨步骤任务，使用执行式评价 | 通过测试就能安全操作真实用户电脑 |

工具评测应分别记录是否选对、参数是否正确、是否实际执行、最终任务是否成功；GUI/网页任务还需保证环境可重置以及执行前后状态一致。不同 benchmark 的子集和协议不同，**pass@k 与 τ-bench 中的 pass^k 含义也不同**：前者通常关心 k 次至少一次成功，后者考察多次执行均成功等可靠性定义，应以对应论文或实现为准。

**评测框架**如 Ragas、DeepEval 可提供数据结构、指标或调用流程；框架本身不是有效性保证。实际面试优先讲任务集、判据、分层评估、数据泄漏和对照，再讲用过哪个框架。
